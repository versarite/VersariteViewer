Writing a native Free Pascal implementation for true lossless JPEG transformation is a great choice. It keeps Versarite-MView completely portable and dependency-free, avoiding the need to ship a separate jpegtran.exe binary.
To implement this natively in Pascal without re-encoding, your code must perform Huffman decoding, manipulate the coefficient arrays of the Entropy-Coded Segments (ECS), and then rewrite the data. It bypasses the Inverse Discrete Cosine Transform (IDCT) and quantization steps, preserving 100% of the original image quality.
The core math and structural steps required to build a native Free Pascal unit for lossless rotation break down into specific tasks:
## 1. The Mathematical Grid Manipulation (The Logic)
Because JPEGs are stored in 8x8 or 16x16 Minimum Coded Units (MCUs), rotating the image requires you to change both the global arrangement of the blocks and the internal structure of each block.
For a 90-degree clockwise rotation, you apply the following operations to the data arrays:

* Block Position Remapping: A block at position (X, Y) moves to a new position (NewX, NewY), where NewX = (HeightInBlocks - 1) - Y and NewY = X.
* Internal Block Transposition: Inside each 8x8 block coefficient matrix, you transpose the matrix (swap rows with columns: $M[i][j] \to M[j][i]$).
* Sign Reversal: To account for the directional orientation change after transposition, you must reverse the signs of the odd-indexed rows or columns depending on whether you are rotating clockwise or counterclockwise.

## 2. Structural Code Steps for the Pascal Unit
To handle this inside your Free Pascal environment, you will structure a custom decoder/encoder pass using a stream object (TMemoryStream or TFileStream).

## 3. Edge Cases Your Code Must Handle
Writing this purely in Pascal means handling the quirks of the JPEG format specification that wrappers usually hide:

* Non-Multiple of 8/16 Dimensions: If your image dimensions are not perfectly divisible by the MCU size (e.g., a width of 1021 pixels instead of 1024), the rightmost edge contains a partial "dropped" block. When rotating 90 degrees, that partial block moves to the bottom edge. You must account for padding adjustment in your block-grabbing array logic to prevent corruption or edge shifts.
* Chroma Subsampling (MCU Sizes): If the image uses YUV 4:2:0 subsampling, a single MCU is actually 16x16 pixels (composed of four Y blocks, one Cb block, and one Cr block). Your block remapping grid must traverse the coefficients in groups of these macro-blocks rather than simple 8x8 blocks, or the color channels will desynchronize from the brightness canvas.
